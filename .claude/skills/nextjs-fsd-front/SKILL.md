# Next.js FSD 관리자 프론트

## 이 스킬을 사용할 때

- FSD 레이어(`app`, `pages`, `widgets`, `features`, `entities`, `shared`) 아래의 파일을 변경할 때 사용한다.
- Next.js 라우팅, 레이아웃, 페이지 조합, 프론트엔드 아키텍처와 관련된 작업에 사용한다.
- 사용자가 FSD 구조에서 코드의 배치 위치를 물을 때 사용한다.

레이어 정의, 의존 방향, 스택 버전은 `.claude/rules/project-architecture.md`가 단일 기준이다. 이 스킬은 그 규칙을 실제 작업 절차로 옮긴 것이다.

## 작업 흐름

1. `.claude/rules/project-architecture.md`에서 레이어 정의와 의존 방향을 확인한다.
2. 같은 FSD 레이어에서 가장 가까운 기존 구현을 찾는다.
3. Next.js 동작을 변경하는 작업이면 수정 전에 `node_modules/next/dist/docs/`의 관련 문서를 읽는다.
4. 해당 동작을 소유하는 **가장 낮은** 레이어를 선택한다.
5. 요청을 만족하는 가장 작은 코드 변경을 수행한다.
6. `npm run lint`를 실행한다.
7. 라우팅, 레이아웃, 설정, 서버/클라이언트 컴포넌트 경계가 변경되면 `npm run build`를 실행한다.

## 배치 가이드

| 대상 | 레이어 |
|---|---|
| 라우트, 레이아웃, 템플릿, 전역 프로바이더 | `app` |
| 페이지 단위 화면 조합 | `pages` |
| 사이드바, 헤더, 대시보드 패널 등 큰 재사용 블록 | `widgets` |
| 상품 등록, 주문 상태 변경, 회원 검색 등 운영자 액션 | `features` |
| `product`, `order`, `member`, `category` 등 도메인 타입과 모델 수준 UI | `entities` |
| API 클라이언트, 공통 유틸리티, 공통 설정, 기본 UI 요소 | `shared` |

## 레이어 판단 기준

- 특정 도메인 하나에만 의미가 있는 코드 → `entities`
- 사용자가 수행하는 동작 하나를 나타내는 코드 → `features`
- 여러 기능과 도메인 모델을 묶어 화면 블록을 구성하는 코드 → `widgets`
- 도메인 지식이 없는 코드 → `shared`

레이어를 판단하기 어려우면 **사용처에 더 가까운 위치**에 둔다. 두 번째 사용처가 생기면 공통으로 사용할 수 있는 하위 레이어로 옮긴다.

## [금지사항]

- FSD 의존 방향을 역행하는 import를 만들지 않는다.
- 사용처가 하나뿐인 코드를 `shared`로 올리지 않는다.
- `src/app` 밖에 별도 라우팅 규칙을 만들지 않는다.
- 사용자가 요청하지 않는 한 상태 관리 라이브러리, 요청 라이브러리, 포매터, 테스트 프레임워크를 새로 도입하지 않는다.
- 기존 코드가 이 규칙을 위반하더라도 요청된 변경을 막지 않으면 고치지 않는다. 별도로 언급만 한다.
- 아직 만들어지지 않은 레이어 디렉토리를, 이번 작업에 실제로 필요하지 않은데 미리 만들지 않는다.
